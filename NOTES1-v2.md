## 1. Transactional Job Queuing via `SKIP LOCKED`

### Theoretical Foundation
A multi-producer, multi-consumer job queue requires two guarantees:
1. **At-most-once delivery per claim attempt**: No two workers should ever claim the same job concurrently.
2. **Non-blocking high-throughput concurrency**: When multiple workers attempt to dequeue work simultaneously, workers must not block behind each other or suffer lock serialization bottlenecks on the head of the table.

Traditional SQL row locking (`SELECT ... FOR UPDATE`) blocks subsequent queries until the first transaction commits or rolls back, serializing worker throughput. In contrast, `SELECT ... FOR UPDATE SKIP LOCKED` instructs the database engine to traverse the index and skip any rows currently locked by other concurrent transactions, locking the next available unlocked candidate row.

### Implementation in YuktiCode v2
The queue claiming logic is encapsulated in [`backend/server/jobs.py:27-58`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/jobs.py#L27-L58) within `claim_job()`:

```sql
WITH next AS (
    SELECT id
    FROM judge_jobs
    WHERE status = 'queued'
      AND available_at <= now()
    ORDER BY priority, available_at, created_at
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE judge_jobs AS j
SET status = 'running',
    locked_by = :worker_id,
    locked_until = now() + make_interval(secs => :lease_seconds),
    attempts = j.attempts + 1,
    updated_at = now()
FROM next
WHERE j.id = next.id
RETURNING j.*
```

Supported by the composite B-Tree index in [`backend/server/db/models.py:180`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/db/models.py#L180):
```python
Index("ix_judge_jobs_claim", "status", "available_at", "priority", "created_at")
```

### Trade-offs & Operational Ceilings
- **Advantage**: Zero extra infrastructure (no Redis, no RabbitMQ). Transactional enrollment: an incoming submission and its corresponding judge job are committed inside the exact same ACID database transaction in [`backend/server/routes.py:160-176`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/routes.py#L160-L176), making "lost jobs" or "orphaned submission records" impossible.
- **Where it fails**: High queue depths ($>100,000$ active rows) create MVCC table bloat in Postgres. While the index keeps the query fast, dead tuples generated by rapid `UPDATE` statements require aggressive autovacuum tuning. At tens of thousands of jobs per second, dedicated broker topologies (Kafka/RabbitMQ) outperform relational disk I/O.

## 2. Distributed Leases & Crash-Resilient Worker Heartbeats

### Theoretical Foundation
In distributed systems without shared memory, if a worker crashes (power failure, kernel panic, out-of-memory kill) while executing a claimed job, the system must detect worker failure and transition the stalled unit of work back to a schedulable state. Distributed leases grant execution rights for a bounded wall-clock duration (`locked_until`). If the lease expires before completion, the lease is considered abandoned.

### Implementation in YuktiCode v2
In [`backend/server/jobs.py:170-240`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/jobs.py#L170-L240), `requeue_expired_jobs()` handles lease expiration:

```python
# 1. Retryable jobs: return to queue and clear lease
retried = await db.execute(
    text("""
        UPDATE judge_jobs
        SET status = 'queued',
            locked_by = NULL,
            locked_until = NULL,
            available_at = now(),
            last_error = 'worker lease expired',
            updated_at = now()
        WHERE status = 'running'
          AND locked_until < now()
          AND attempts < :max_attempts
        RETURNING id
    """),
    {"max_attempts": JOB_MAX_ATTEMPTS},  # default 3
)

# 2. Poison jobs (attempts >= max_attempts): transition to dead-letter state
failed = await db.execute(
    text("""
        UPDATE judge_jobs
        SET status = 'failed',
            result = CAST(:result AS json),
            last_error = 'worker lease expired after max attempts',
            locked_by = NULL,
            locked_until = NULL,
            updated_at = now()
        WHERE status = 'running'
          AND locked_until < now()
          AND attempts >= :max_attempts
        RETURNING id
    """),
    {"max_attempts": JOB_MAX_ATTEMPTS, "result": json.dumps({"status": "SYSTEM_ERROR", "message": "Execution timed out repeatedly across multiple workers."})},
)
```

Each recovery event increments the Prometheus counter `judge_worker_requeued_leases_total` ([`backend/worker/main.py:192`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/worker/main.py#L192)) to alert SREs of crash loops.

## 3. OS-Level Container Sandboxing & Resource Isolation

### Theoretical Foundation
Executing untrusted, user-submitted code in an online judge represents an adversarial computing environment. The execution sandbox must defend against:
1. **Network attacks**: Port scanning, C2 beaconing, lateral movement.
2. **Denial of Service**: Fork bombs, CPU exhaustion, host memory starvation.
3. **Privilege Escalation**: Breaking out of container namespaces via kernel exploits.
4. **Host Disk Saturation**: Infinite file writes (`while(1) printf(...)`).

## 4. Zero-Knowledge Oracle Pattern (Information Hiding)

### Theoretical Foundation
In traditional sandbox designs, expected outputs (`output.txt`) are copied into the sandbox container alongside test inputs (`input.txt`), and a diff script evaluates correctness inside the container. This creates an existential security flaw: malicious code can inspect the filesystem, read `/workspace/output.txt`, and print the answer verbatim, achieving a false `Accepted` verdict.

### Implementation in YuktiCode v2
YuktiCode v2 implements the **Zero-Knowledge Oracle** pattern ([`backend/worker/judger.py:240-270`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/worker/judger.py#L240-L270)):
1. Only the candidate source (`main.cpp`) and the test input (`input.txt`) enter the container via stdin streams.
2. The expected output **never** enters the container filesystem or memory.
3. The candidate process executes, writes to `stdout.txt`, and terminates.
4. The worker daemon reads `stdout.txt` from the container, streams it back to the host, and executes `compare_outputs(expected_output, actual_output)` entirely in the trusted host worker process ([`backend/worker/judger.py:12-25`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/worker/judger.py#L12-L25)):
```python
def compare_outputs(expected: str, actual: str) -> bool:
    def lines(s: str):
        for line in s.replace("\r\n", "\n").replace("\r", "\n").split("\n"):
            stripped = line.rstrip()
            if stripped:
                yield stripped
    return list(lines(expected)) == list(lines(actual))
```

## 5. Optimistic Concurrency & Idempotent State Transitions

### Theoretical Foundation
In distributed computing, duplicate execution of work is inevitable when network partitions or transient slowdowns occur (the "at-least-once" delivery phenomenon). Idempotence ensures that applying the same state change multiple times leaves the system in the identical valid state. Optimistic Concurrency Control (OCC) verifies that the assumptions under which an operation began are still true before writing the result.

### Implementation in YuktiCode v2
In [`backend/server/jobs.py:69-120`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/jobs.py#L69-L120), `complete_job()` executes dual optimistic concurrency guards:

```python
# Guard 1: Verify this worker still holds the valid active lease
updated = await db.execute(
    text("""
        UPDATE judge_jobs
        SET status = 'done',
            result = CAST(:result AS json),
            locked_by = NULL,
            locked_until = NULL,
            updated_at = now()
        WHERE id = :job_id
          AND status = 'running'
          AND locked_by = :worker_id
    """),
    {"job_id": job_id, "worker_id": worker_id, "result": json.dumps(_json_safe(result))},
)
if not updated.rowcount:
    # Another worker already re-claimed or re-queued this lease.
    await db.rollback()
    return

# Guard 2: Submission terminal state immutability
if submission_id is not None:
    status = str(result.get("status", "SYSTEM_ERROR"))
    await db.execute(
        text("""
            UPDATE submissions
            SET status = :status,
                execution_time_ms = :time_ms,
                peak_memory_mb = :mem_mb,
                message = :message
            WHERE id = :submission_id
              AND status = 'PENDING'
        """),
        {"submission_id": submission_id, "status": status, ...},
    )
await db.commit()
```

## 6. Sliding-Window Rate Limiting & Reverse-Proxy Trust Boundaries

### Theoretical Foundation
Authentication endpoints are susceptible to brute-force credential stuffing. Fixed-window limiters suffer from boundary bursts (double the allowed requests at the window boundary). A **sliding-window log** algorithm maintains timestamps of requests over a continuous moving interval, guaranteeing the rate limit holds across any arbitrary time slice.

### Implementation in YuktiCode v2
Implemented in [`backend/server/auth.py:28-123`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/auth.py#L28-L123):

```python
_LOGIN_WINDOW_SECONDS = 300   # 5-minute window
_LOGIN_MAX_ATTEMPTS = 10      # Max 10 failed attempts
_login_attempts: dict[str, deque[float]] = defaultdict(deque)
_login_lock = asyncio.Lock()

async def _check_login_rate_limit(key: str) -> None:
    now = time.monotonic()
    async with _login_lock:
        bucket = _login_attempts[key]
        while bucket and now - bucket[0] > _LOGIN_WINDOW_SECONDS:
            bucket.popleft()  # Prune timestamps outside window
        if len(bucket) >= _LOGIN_MAX_ATTEMPTS:
            raise HTTPException(status_code=429, detail="Too many login attempts; try again later.")
```

## 9. Storage-Layer Fault Normalization (NUL Byte Sanitization)

### Theoretical Foundation
PostgreSQL terminates C-strings at the first `\x00` (NUL) byte. In PostgreSQL, attempting to insert a string containing `\x00` into a `text` or `json` column raises an unhandled database exception (`unsupported Unicode escape sequence \u0000`). Malicious candidate code can intentionally print raw binary memory or NUL bytes to crash the judge worker during verdict persistence.

### Implementation in YuktiCode v2
In [`backend/server/jobs.py:16-24`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/jobs.py#L16-L24):
```python
def _json_safe(value):
    """Postgres text/json cannot store NUL bytes; strip them recursively."""
    if isinstance(value, str):
        return value.replace("\x00", "")
    if isinstance(value, dict):
        return {key: _json_safe(item) for key, item in value.items()}
    if isinstance(value, (list, tuple)):
        return [_json_safe(item) for item in value]
    return value
```

## 11. Event-Driven Autoscaling (Queue Backlog Lag vs CPU/Memory HPA)

### Theoretical Foundation
In queue-driven asynchronous systems, scaling decisions must be based on **queue backlog latency (Little's Law)** rather than resource utilization:

$$L = \lambda W$$

Where:
- $L$ is the number of queued units of work.
- $\lambda$ is the submission arrival rate.
- $W$ is the average execution time per submission.

#### The Failure of CPU/Memory-based HPA in Judge Platforms
Standard Kubernetes Horizontal Pod Autoscaling (HPA) uses average Pod CPU or Memory. For an online judge, this fails catastrophically:
1. **Compilation Burst Noise**: A candidate submitting a single C++ file consumes 100% of one CPU core for 1.2 seconds during compilation. A CPU-based autoscaler interprets this as node saturation and immediately spins up 3 new pods, even though the queue is empty.
2. **Lagging Saturation**: When 100 students submit simultaneously at the start of a contest, submissions sit in the PostgreSQL queue waiting for workers. Because workers are busy processing the first 2 jobs, the remaining 98 jobs cause zero CPU consumption on unspawned pods. CPU HPA sees "normal" CPU and delays scaling until candidate latency has already violated SLOs.

### Implementation in YuktiCode v2
YuktiCode v2 integrates **KEDA (Kubernetes Event-driven Autoscaling)** ([`deploy/k8s/keda-scaledobject.yaml`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/deploy/k8s/keda-scaledobject.yaml)):

$$\text{Desired Replicas} = \max\left(\text{minReplicas}, \min\left(\text{maxReplicas}, \left\lceil \frac{\text{Backlog}}{\text{targetQueryValue}} \right\rceil\right)\right)$$

```yaml
triggers:
  - type: postgresql
    metadata:
      connectionFromEnv: DATABASE_URL_PG
      query: "SELECT count(*) FROM judge_jobs WHERE status = 'queued' AND available_at <= now();"
      targetQueryValue: "5"
      activationTargetQueryValue: "1"
```
- **Leading Indicator**: KEDA scales based on unhandled work ($5\text{ jobs / worker}$), ensuring replica capacity expands *before* latency spikes.
- **Cooldown & Hysteresis**: A 30-second `cooldownPeriod` dampens scale-down thrashing when jobs finish in bursts.

## 12. The RED Method & Distributed Queue Observability (Pull vs Push)

### Theoretical Foundation
Production systems require distinct observability paradigms for synchronous edge ingress vs. asynchronous background processing:
1. **The RED Method (Ingress)**:
   - **Rate**: Throughput in requests per second.
   - **Errors**: Number of failed requests (HTTP 4xx / 5xx).
   - **Duration**: Distribution of request latencies (p50, p95, p99 percentiles).
2. **The USE Method (Asynchronous Queue & Storage)**:
   - **Utilization**: Percentage of time workers are busy vs idling.
   - **Saturation**: PostgreSQL queue backlog depth (`judge_queue_depth{status="queued"}`).
   - **Errors**: Dead-letter jobs and lease recovery counts.

### Implementation in YuktiCode v2

#### Ingress Telemetry Middleware ([`backend/server/metrics.py`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/metrics.py))
`PrometheusMiddleware` intercepts all HTTP requests, recording metrics to standard Prometheus registries:
- `http_requests_total`
- `http_request_duration_seconds` (histogram with buckets from 5ms to 5.0s)

#### Safe Asynchronous Queue Telemetry Collector
On every scrape of `GET /metrics`:
```python
async def update_queue_metrics():
    async with async_session_maker() as session:
        result = await session.execute(
            text("SELECT status, count(*) FROM judge_jobs GROUP BY status")
        )
        for s in ("queued", "running", "done", "failed"):
            JUDGE_QUEUE_DEPTH.labels(status=s).set(0)
        for row in result.all():
            JUDGE_QUEUE_DEPTH.labels(status=row[0]).set(row[1])
```
- **Zero Lock Contention**: The query aggregates status counts without taking row locks or interfering with worker `FOR UPDATE SKIP LOCKED` claims.

#### Why Pull-Based Prometheus Over Push-Based Metrics
1. **Zero Backpressure**: In push models (e.g. StatsD, CloudWatch API calls), if the telemetry endpoint slows down, the worker thread blocks or leaks memory buffering metrics. With pull-based Prometheus, the scraper absorbs network latency; the worker simply updates in-memory atomic counters.
2. **Crash Resilience**: If a worker daemon dies, Prometheus immediately detects target failure (`up == 0`), providing instant liveness detection without custom heartbeats.

## 13. Concepts Deliberately Not Used (And Why)

| Concept / Technology | Why an Interviewer Might Expect It | Why It Is Deliberately Omitted in YuktiCode v2 |
|---|---|---|
| **Push-Based Telemetry (StatsD / Pushgateway)** | Pushing metrics to a central collector over UDP/HTTP. | **Egress Backpressure & Memory Leak Risk.** Push systems can block worker threads or drop metrics during network congestion. The pull model keeps workers 100% decoupled from the telemetry collector. |
| **CPU/Memory Horizontal Pod Autoscaler (HPA)** | Standard Kubernetes scaling on pod CPU usage. | **Lagging Indicator & False Positives.** Compilation utilizes 100% of 1 core briefly, causing false-positive pod scale-outs. Queue backlog depth is the only true leading indicator for asynchronous batch workers. |
| **Redis / Memcached** | Caching problem statements, session store, rate limit keys, or leaderboard caches. | **Eliminated Cache Invalidation & Extra Service.** Problem statements change infrequently; Postgres memory buffers (`shared_buffers`) cache hot rows in RAM automatically. Adding Redis introduces cache invalidation bugs and an additional stateful service to monitor and backup. |
| **RabbitMQ / Kafka / Celery** | Standard asynchronous queue brokers for heavy background tasks. | **Eliminated Dual-Write / Two-Phase Commit.** In an online judge, an enqueue operation must be consistent with the database submission insert. With an external broker, if the database insert succeeds but the broker enqueue fails, the submission is stuck in `PENDING` forever. Postgres `judge_jobs` table provides zero-latency transactional enqueuing in the exact same transaction. |
| **WebSockets / Server-Sent Events** | Real-time push notifications of submission verdicts to the browser. | **Stateless Edge Simplicity.** Long-lived stateful connections tie up socket descriptors on reverse proxies and require horizontal pub/sub infrastructure (e.g. Redis Pub/Sub). Short polling at 1.0s over HTTP keep-alive uses established connections, is resilient to client network hops, and keeps the API tier 100% stateless. |
| **Distributed Locks (Redlock / etcd)** | Preventing multiple workers from picking up the same job. | **Replaced by Postgres Row Locks (`SKIP LOCKED`).** PostgreSQL provides ACID row locking native to the relational engine. Redlock has well-documented edge cases under clock drift and network pauses. Postgres row locks are automatically released if the client connection drops. |
| **Separate Reaper Daemon** | Periodic cron job or Celery beat process to recover dead jobs and orphaned containers. | **Integrated into Worker Run Loop.** Having a separate reaper process introduces another service dependency. Instead, the worker run loop executes `requeue_expired_jobs()` on every iteration and `reap_orphaned_containers()` every 300 seconds ([`backend/worker/main.py:186-203`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/worker/main.py#L186-L203)), guaranteeing self-healing. |
| **Static Code Analysis / AST Inspection** | Rejecting dangerous Python imports (`import os`, `import subprocess`) before execution. | **Trivial to Bypass.** Blacklisting imports via AST parsing is notorious for being bypassed via reflection, dynamic imports (`__import__`), or bytecode manipulation (`eval`, `globals()`). YuktiCode v2 treats all user code as fundamentally hostile and relies entirely on OS-level sandboxing (network-less, read-only root, dropped capabilities, unprivileged user). |
| **Warm / Pre-Forked Container Pools** | Keeping long-running containers alive to eliminate Docker container startup overhead. | **Tainted State Risk.** Reusing a container across test cases risks data leakage or state pollution (e.g. leftover files in `/tmp` or background daemon processes spawned by the candidate). Creating a fresh container per test case guarantees a mathematically clean, unpolluted sandbox environment. |
