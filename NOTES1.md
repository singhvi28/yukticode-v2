## 1. Transactional Job Queuing via `SKIP LOCKED`

### Theoretical Foundation
A multi-producer, multi-consumer job queue requires two guarantees:
1. **At-most-once delivery per claim attempt**: No two workers should ever claim the same job concurrently.
2. **Non-blocking high-throughput concurrency**: When multiple workers attempt to dequeue work simultaneously, workers must not block behind each other or suffer lock serialization bottlenecks on the head of the table.

Traditional SQL row locking (`SELECT ... FOR UPDATE`) blocks subsequent queries until the first transaction commits or rolls back, serializing worker throughput. In contrast, `SELECT ... FOR UPDATE SKIP LOCKED` instructs the database engine to traverse the index and skip any rows currently locked by other concurrent transactions, locking the next available unlocked candidate row.

### Implementation in YuktiCode v2
The queue claiming logic is encapsulated in [`backend/server/jobs.py:27-58`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/jobs.py#L27-L58) within `claim_job()`:

```sql
WITH next AS (
    SELECT id
    FROM judge_jobs
    WHERE status = 'queued'
      AND available_at <= now()
    ORDER BY priority, available_at, created_at
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE judge_jobs AS j
SET status = 'running',
    locked_by = :worker_id,
    locked_until = now() + make_interval(secs => :lease_seconds),
    attempts = j.attempts + 1,
    updated_at = now()
FROM next
WHERE j.id = next.id
RETURNING j.*
```

Supported by the composite B-Tree index in [`backend/server/db/models.py:180`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/db/models.py#L180):
```python
Index("ix_judge_jobs_claim", "status", "available_at", "priority", "created_at")
```

### Trade-offs & Operational Ceilings
- **Advantage**: Zero extra infrastructure (no Redis, no RabbitMQ). Transactional enrollment: an incoming submission and its corresponding judge job are committed inside the exact same ACID database transaction in [`backend/server/routes.py:160-176`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/routes.py#L160-L176), making "lost jobs" or "orphaned submission records" impossible.
- **Where it fails**: High queue depths ($>100,000$ active rows) create MVCC table bloat in Postgres. While the index keeps the query fast, dead tuples generated by rapid `UPDATE` statements require aggressive autovacuum tuning. At tens of thousands of jobs per second, dedicated broker topologies (Kafka/RabbitMQ) outperform relational disk I/O.

## 2. Distributed Leases & Crash-Resilient Worker Heartbeats

### Theoretical Foundation
In distributed systems without shared memory, if a worker crashes (power failure, kernel panic, out-of-memory kill) while executing a claimed job, the system must detect worker failure and transition the stalled unit of work back to a schedulable state. Distributed leases grant execution rights for a bounded wall-clock duration (`locked_until`). If the lease expires before completion, the lease is considered abandoned.

### Implementation in YuktiCode v2
In [`backend/server/jobs.py:170-240`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/jobs.py#L170-L240), `requeue_expired_jobs()` handles lease expiration:

```python
# 1. Retryable jobs: return to queue and clear lease
retried = await db.execute(
    text("""
        UPDATE judge_jobs
        SET status = 'queued',
            locked_by = NULL,
            locked_until = NULL,
            available_at = now(),
            last_error = 'worker lease expired',
            updated_at = now()
        WHERE status = 'running'
          AND locked_until < now()
          AND attempts < :max_attempts
        RETURNING id
    """),
    {"max_attempts": JOB_MAX_ATTEMPTS},  # default 3
)

# 2. Poison jobs (attempts >= max_attempts): transition to dead-letter state
failed = await db.execute(
    text("""
        UPDATE judge_jobs
        SET status = 'failed',
            result = CAST(:result AS json),
            last_error = 'worker lease expired after max attempts',
            locked_by = NULL,
            locked_until = NULL,
            updated_at = now()
        WHERE status = 'running'
          AND locked_until < now()
          AND attempts >= :max_attempts
        RETURNING id, kind, submission_id
    """),
    {"max_attempts": JOB_MAX_ATTEMPTS, "result": json.dumps({"status": "SYSTEM_ERROR", ...})},
)
```

Crucially, every worker run loop invokes `requeue_expired_jobs()` right before claiming work ([`backend/worker/main.py:163`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/worker/main.py#L163)). There is no separate reaper daemon; active workers continuously self-heal the queue.

### Trade-offs & Operational Ceilings
- **Advantage**: Simplicity and crash resilience. If a worker process is abruptly killed with `SIGKILL`, the job is neither permanently lost nor stuck in `running`.
- **Where it fails**: Clock drift between server nodes can trigger premature lease reclamation if NTP is not synchronized. Furthermore, if a job naturally requires longer than `JOB_LEASE_SECONDS` (600s), another worker may reclaim it while the first worker is still computing, leading to redundant work.

## 3. OS-Level Container Sandboxing & Resource Isolation

### Theoretical Foundation
Online judges run untrusted arbitrary code submitted by adversarial actors. Security relies on **defense-in-depth**: layering multiple independent Linux kernel isolation primitives so that a compromise of one layer does not yield host root execution or network ingress/egress.

### Implementation in YuktiCode v2
In [`backend/worker/judger.py:178-223`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/worker/judger.py#L178-L223), every test case spawns a transient container with strict isolation properties:

```python
kwargs = {
    "image": image,                                        # Debian Bookworm slim
    "command": ["sleep", "infinity"],
    "detach": True,
    "network_mode": "none",                                # Network namespace unshared (no lo routing)
    "read_only": True,                                     # Root filesystem mounted MS_RDONLY
    "user": "65534:65534",                                 # nobody:nogroup unprivileged user
    "cap_drop": ["ALL"],                                   # Drops ALL capabilities (no CAP_SYS_ADMIN, etc.)
    "security_opt": ["no-new-privileges"],                 # PR_SET_NO_NEW_PRIVS (blocks setuid escalation)
    "pids_limit": 64,                                      # PID cgroup max process ceiling (anti-forkbomb)
    "mem_limit": f"{memory_limit_mb}m",                    # Memory cgroup ceiling
    "memswap_limit": f"{memory_limit_mb}m",                # Swap memory disabled
    "nano_cpus": 1_000_000_000,                            # CPU quota: exactly 1 core
    "ulimits": [
        Ulimit(name="nofile", soft=256, hard=256),         # File descriptor limit
        Ulimit(name="fsize", soft=2*1024*1024, hard=2*1024*1024), # 2MB maximum file generation
    ],
    "tmpfs": {
        "/workspace": "rw,nosuid,nodev,exec,mode=1777,size=64m",
        "/tmp": "rw,nosuid,nodev,mode=1777,size=64m",
        "/dev/shm": "rw,nosuid,nodev,noexec,mode=1777,size=32m",
    },
    "environment": {"HOME": "/tmp", "PYTHONDONTWRITEBYTECODE": "1"},
    "working_dir": "/workspace",
}
```

#### Layer Breakdown:
1. **Network Namespace (`network_mode: none`)**: Prevents candidate code from connecting to internal network infrastructure (PostgreSQL, Docker socket, cloud instance metadata services at `169.254.169.254`).
2. **Mount Namespace & Read-Only Root (`read_only: True`)**: System binaries (`/bin`, `/usr`) cannot be replaced or infected with rootkits. Writable space is strictly confined to memory-backed `tmpfs`.
3. **Capability Dropping (`cap_drop: ["ALL"]`)**: Eliminates the ability to mount filesystems, alter network interfaces, inject raw sockets, or trace processes (`ptrace`).
4. **PID Cgroup (`pids_limit: 64`)**: Defeats fork bombs (`while(1) fork();`). When process count reaches 64, `clone()` returns `-EAGAIN`.
5. **Memory Cgroup (`mem_limit` == `memswap_limit`)**: Prevents untrusted programs from causing host kernel out-of-memory panics. If user memory exceeds the problem limit, the Linux cgroup OOM killer terminates the process with exit code 137 (`MLE`).
6. **Virtualization Extensibility (`runsc` / gVisor)**: If installed, auto-detected via [`_runtime()`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/worker/judger.py#L58-L67), running the container inside an unprivileged user-space kernel (Sentry), fully intercepting system calls.

## 4. Zero-Knowledge Oracle Pattern (Information Hiding)

### Theoretical Foundation
In an online judge, the most common security vulnerability is a candidate extracting secret test cases:
1. By reading expected output files from disk or memory.
2. By reading environment variables or command-line parameters of parent processes (`/proc/$PPID/cmdline`).

The **Zero-Knowledge Oracle Pattern** dictates that untrusted code must be completely blind to the expected output. The candidate code produces an output against a given input; verification against the gold standard must occur exclusively in an external, higher-privilege supervision context.

### Implementation in YuktiCode v2
In [`backend/worker/judger.py:70-75`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/worker/judger.py#L70-L75):
```python
def _files(source: str, stdin: str, language: str) -> list[tuple[str, bytes]]:
    """Exactly the two files the candidate should see, never expected output."""
    return [
        (_SOURCE_FILES[language], (source or "").encode("utf-8")),
        ("input.txt", (stdin or "").encode("utf-8")),
    ]
```
The expected output is never written into the container filesystem, never mounted via volume, and never piped through exec stdin. Once the candidate container finishes writing `/workspace/stdout.txt`, the worker host reads the text via [`_read_bytes()`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/worker/judger.py#L111-L129) and performs the comparison on the host via `compare_outputs()`:

```python
# backend/worker/judger.py:139-150
def compare_outputs(expected: str, actual: str) -> bool:
    def lines(text: str):
        values = text.replace("\r\n", "\n").replace("\r", "\n").split("\n")
        start, end = 0, len(values) - 1
        while start <= end and values[start].strip() == "":
            start += 1
        while end >= start and values[end].strip() == "":
            end -= 1
        for index in range(start, end + 1):
            yield values[index].rstrip()

    return list(lines(expected)) == list(lines(actual))
```
Notice that output comparison normalizes CRLF and ignores trailing blank lines while strictly preserving internal whitespaces and token sequences.

## 5. Optimistic Concurrency & Idempotent State Transitions

### Theoretical Foundation
In distributed computing, duplicate execution of work is inevitable when network partitions or transient slowdowns occur (the "at-least-once" delivery phenomenon). Idempotence ensures that applying the same state change multiple times leaves the system in the identical valid state. Optimistic Concurrency Control (OCC) verifies that the assumptions under which an operation began are still true before writing the result.

### Implementation in YuktiCode v2
In [`backend/server/jobs.py:69-120`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/jobs.py#L69-L120), `complete_job()` executes dual optimistic concurrency guards:

```python
# Guard 1: Verify this worker still holds the valid active lease
updated = await db.execute(
    text("""
        UPDATE judge_jobs
        SET status = 'done',
            result = CAST(:result AS json),
            locked_by = NULL,
            locked_until = NULL,
            updated_at = now()
        WHERE id = :job_id
          AND status = 'running'
          AND locked_by = :worker_id
    """),
    {"job_id": job_id, "worker_id": worker_id, "result": json.dumps(_json_safe(result))},
)
if not updated.rowcount:
    # Another worker already re-claimed or re-queued this lease.
    await db.rollback()
    return

# Guard 2: Submission terminal state immutability
if submission_id is not None:
    status = str(result.get("status", "SYSTEM_ERROR"))
    await db.execute(
        text("""
            UPDATE submissions
            SET status = :status,
                execution_time_ms = :time_ms,
                peak_memory_mb = :mem_mb,
                message = :message
            WHERE id = :submission_id
              AND status = 'PENDING'
        """),
        {"submission_id": submission_id, "status": status, ...},
    )
await db.commit()
```

If a duplicate or late-arriving completion message arrives, Guard 1 detects that the row's `locked_by` has changed, immediately rolling back the transaction. Guard 2 ensures that a submission that was already finalized never has its verdict mutated.

## 6. Sliding-Window Rate Limiting & Reverse-Proxy Trust Boundaries

### Theoretical Foundation
Authentication endpoints are susceptible to brute-force credential stuffing. Fixed-window limiters suffer from boundary bursts (double the allowed requests at the window boundary). A **sliding-window log** algorithm maintains timestamps of requests over a continuous moving interval, guaranteeing the rate limit holds across any arbitrary time slice.

### Implementation in YuktiCode v2
Implemented in [`backend/server/auth.py:28-123`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/auth.py#L28-L123):

```python
_LOGIN_WINDOW_SECONDS = 300   # 5-minute window
_LOGIN_MAX_ATTEMPTS = 10      # Max 10 failed attempts
_login_attempts: dict[str, deque[float]] = defaultdict(deque)
_login_lock = asyncio.Lock()

async def _check_login_rate_limit(key: str) -> None:
    now = time.monotonic()
    async with _login_lock:
        bucket = _login_attempts[key]
        while bucket and now - bucket[0] > _LOGIN_WINDOW_SECONDS:
            bucket.popleft()  # Prune timestamps outside window
        if len(bucket) >= _LOGIN_MAX_ATTEMPTS:
            raise HTTPException(status_code=429, detail="Too many login attempts; try again later.")
```

#### Trust Boundary: Client IP Derivation
A frequent flaw in rate limiters is spoofable `X-Forwarded-For` headers. YuktiCode v2 establishes a clear architectural trust boundary at Nginx ([`frontend/nginx.conf:45`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/frontend/nginx.conf#L45)):
```nginx
proxy_set_header X-Real-IP $remote_addr;
```
FastAPI never exposes its port to the public host network in Docker Compose (it is on an internal Docker network, reachable only by Nginx). FastAPI can therefore safely trust `X-Real-IP` ([`backend/server/auth.py:116-123`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/auth.py#L116-L123)):
```python
def _login_key(request: Request, username: str) -> str:
    client = request.headers.get("x-real-ip") or (
        request.client.host if request.client else "unknown"
    )
    return f"{client}:{username.lower()}"
```
The composite key `ip:username` prevents a distributed botnet from locking out an innocent user while simultaneously preventing a single attacker from brute-forcing passwords across multiple user accounts from one IP.

## 7. Dynamic Compute-on-Read Standings (Pure State Projections)

### Theoretical Foundation
In traditional web architectures, contest standings are often maintained incrementally (e.g. updating a Redis Sorted Set or a denormalized table whenever a submission finishes). However, online judges face administrative realities:
- A faulty test case is updated, triggering a batch re-judge of hundreds of submissions.
- A problem statement is retracted or an author modifies test limits.
- Plagiarism disqualifications revoke submissions post-contest.

Incremental accumulators risk state drift and corruption when events are replayed or retracted. The **Event Sourcing / Pure State Projection** pattern computes the view dynamically from the canonical event log (the `submissions` table) on demand.

### Implementation in YuktiCode v2
In [`backend/server/leaderboard.py:20-65`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/leaderboard.py#L20-L65), `rank_submissions()` is a pure, side-effect-free function:

```python

    for row in rows:
        key = (row.user_id, row.problem_id)
        state = per_problem.setdefault(key, {"solved": False, "attempts": 0, "first_ac": None})
        if state["solved"]:
            continue  # Submissions after AC are completely ignored
        if row.status == "AC":
            state["solved"] = True
            state["first_ac"] = row.submitted_at
        elif row.status in PENALTY_STATUSES:  # WA, TLE, RE, MLE
            state["attempts"] += 1

    # ICPC Scoring: Points + (minutes elapsed + 20 min * prior wrong attempts)
    ...
    # Deterministic Tie-Breaker
    table.sort(key=lambda row: (-row["score"], row["penalty"], row["last_ac"], row["username"]))
```

Supported by the database query in [`compute_leaderboard()`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/leaderboard.py#L75-L97) utilizing the composite index `("contest_id", "user_id", "problem_id", "submitted_at")`.

### Trade-offs & Operational Ceilings
- **Advantage**: Guaranteed mathematical consistency. Re-judging a submission instantly updates standings with zero cache invalidation logic. Testable via standard unit tests without a database ([`backend/tests/test_leaderboard.py`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/tests/test_leaderboard.py)).
- **Where it fails**: Large global contests ($>10,000$ active contestants, $>500,000$ submissions). In such environments, full table aggregation on every read degrades database latency. At that scale, materialized views refreshed concurrently or an external read-model cache (e.g., Redis zset with replayable sync) becomes necessary.

## 8. Client-Side Monotonic Token Guards for Polling Invalidation

### Theoretical Foundation
Under short polling with asynchronous requests, HTTP responses can arrive out-of-order due to network jitter. If a user triggers Run A, cancels it, and triggers Run B, a delayed response for Run A arriving after Run B must not overwrite the UI with stale data (the classic **Time-of-Check to Time-of-Use / ABA race condition**).

### Implementation in YuktiCode v2
In [`frontend/src/hooks/useSubmission.js:20-91`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/frontend/src/hooks/useSubmission.js#L20-L91) and [`frontend/src/hooks/useRunBatch.js:57-170`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/frontend/src/hooks/useRunBatch.js#L57-L170):

```javascript
const pollTimerRef = useRef(null);
const runTokenRef = useRef(0);

const handleSubmit = useCallback(async (...) => {
    clearTimeout(pollTimerRef.current);
    const token = runTokenRef.current + 1;  // Monotonically increasing generation token
    runTokenRef.current = token;
    ...
    const poll = async () => {
        if (runTokenRef.current !== token) return; // Stale poll loop aborted
        try {
            const res = await api.get(`/submissions/${submissionId}`);
            if (runTokenRef.current !== token) return; // Response arrived after newer click; discard!
            ...
            if (data.status === 'PENDING') {
                pollTimerRef.current = setTimeout(poll, POLL_INTERVAL_MS);
            }
        } catch (err) {
            if (runTokenRef.current !== token) return;
            ...
        }
    };
    poll();
}, []);
```
By comparing closure-captured generation `token` with mutable `runTokenRef.current`, all stale poll cycles are immediately cancelled and cannot mutate the React state tree.

## 9. Storage-Layer Fault Normalization (NUL Byte Sanitization)

### Theoretical Foundation
PostgreSQL stores `text` and `json` as C-strings under the hood, terminating them at the first `\x00` (NUL) byte. In PostgreSQL, attempting to insert a string containing `\x00` into a `text` or `json` column raises an unhandled database exception (`unsupported Unicode escape sequence \u0000`). Malicious candidate code can intentionally print raw binary memory or NUL bytes to crash the judge worker during verdict persistence.

### Implementation in YuktiCode v2
In [`backend/server/jobs.py:16-24`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/jobs.py#L16-L24):

```python
def _json_safe(value):
    """Postgres text/json cannot store NUL bytes; strip them recursively."""
    if isinstance(value, str):
        return value.replace("\x00", "")
    if isinstance(value, dict):
        return {key: _json_safe(item) for key, item in value.items()}
    if isinstance(value, (list, tuple)):
        return [_json_safe(item) for item in value]
    return value
```
Before any verdict payload or execution result is serialized and passed to PostgreSQL via SQL parameters ([`complete_job()`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/jobs.py#L86) and [`fail_job()`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/jobs.py#L148)), it is normalized through `_json_safe()`, preventing SQL driver crashes.

## 10. Fail-Closed Cryptographic Secrets Initialization

### Theoretical Foundation
The **Fail-Safe Defaults / Fail-Closed** security principle states that systems must deny access or abort execution when critical configuration parameters are absent or insecure, rather than falling back to convenient, predictable defaults.

### Implementation in YuktiCode v2
In [`backend/server/config.py:10-26`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/server/config.py#L10-L26):

```python
def _required(name: str) -> str:
    value = os.getenv(name, "").strip()
    if not value:
        raise RuntimeError(
```

## 11. Concepts Deliberately Not Used (And Why)

In an interview, articulating what an architecture **deliberately excludes** demonstrates engineering maturity. YuktiCode v2 explicitly avoids the following industry staples:

| Concept / Technology | Why an Interviewer Might Expect It | Why It Is Deliberately Omitted in YuktiCode v2 |
|---|---|---|
| **Redis / Memcached** | Caching problem statements, session store, rate limit keys, or leaderboard caches. | **Eliminated Cache Invalidation & Extra Service.** Problem statements change infrequently; Postgres memory buffers (`shared_buffers`) cache hot rows in RAM automatically. Adding Redis introduces cache invalidation bugs and an additional stateful service to monitor and backup. |
| **RabbitMQ / Kafka / Celery** | Standard asynchronous queue brokers for heavy background tasks. | **Eliminated Dual-Write / Two-Phase Commit.** In an online judge, an enqueue operation must be consistent with the database submission insert. With an external broker, if the database insert succeeds but the broker enqueue fails (network partition), the submission is stuck in `PENDING` forever. Postgres `judge_jobs` table provides zero-latency transactional enqueuing in the exact same transaction. |
| **WebSockets / Server-Sent Events** | Real-time push notifications of submission verdicts to the browser. | **Stateless Edge Simplicity.** Long-lived stateful connections tie up socket descriptors on reverse proxies and require horizontal pub/sub infrastructure (e.g. Redis Pub/Sub) to fan out worker verdicts to the correct client connection. Short polling at 1.0s over HTTP keep-alive uses established connections, is resilient to client network hops, and keeps the API tier 100% stateless. |
| **Distributed Locks (Redlock / etcd)** | Preventing multiple workers from picking up the same job. | **Replaced by Postgres Row Locks (`SKIP LOCKED`).** PostgreSQL provides ACID row locking native to the relational engine. Redlock has well-documented edge cases under clock drift and network pauses. Postgres row locks are automatically released if the client connection drops. |
| **Separate Reaper Daemon** | Periodic cron job or Celery beat process to recover dead jobs and orphaned containers. | **Integrated into Worker Run Loop.** Having a separate reaper process introduces another service dependency. Instead, the worker run loop executes `requeue_expired_jobs()` on every iteration and `reap_orphaned_containers()` every 300 seconds ([`backend/worker/main.py:163-174`](file:///home/singhvi28/Desktop/dev/cf-clone-v2/backend/worker/main.py#L163-L174)), guaranteeing self-healing. |
| **Static Code Analysis / AST Inspection** | Rejecting dangerous Python imports (`import os`, `import subprocess`) before execution. | **Trivial to Bypass.** Blacklisting imports via AST parsing is notorious for being bypassed via reflection, dynamic imports (`__import__`), or bytecode manipulation (`eval`, `globals()`). YuktiCode v2 treats all user code as fundamentally hostile and relies entirely on OS-level sandboxing (network-less, read-only root, dropped capabilities, unprivileged user). |
| **Warm / Pre-Forked Container Pools** | Keeping long-running containers alive to eliminate Docker container startup overhead. | **Tainted State Risk.** Reusing a container across test cases risks data leakage or state pollution (e.g. leftover files in `/tmp` or background daemon processes spawned by the candidate). Creating a fresh container per test case guarantees a mathematically clean, unpolluted sandbox environment. |
